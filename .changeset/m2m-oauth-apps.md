'@getbrevo/cli': minor
---

`brevo app create` can now create a **machine-to-machine (M2M)** OAuth app — one that uses the `client_credentials` grant, where your own server calls the Brevo API as itself with no Brevo user to redirect and no callback to register. Previously every OAuth app the CLI created was consent-based: it always collected a redirect URI and always sent `auth: { scopes, redirect_uris }`, so a server-to-server integration had to create a consent-based app and ignore half of it.

For a **private** OAuth app the interactive flow now asks *"Which OAuth flow does this app use?"* — *Consent Based* or *Machine to Machine* — after the app-type question and before any callback URL, because the answer decides whether a callback is asked for at all. Non-interactively, pass `--m2m --scopes "contacts:read,crm:read"`. M2M is private-only, `--scopes` is required with `--m2m`, and combining `--m2m` with `--redirect-uri`, `--ui-app`, `--ui-config` or `--distribution public` is refused before anything is created.

**M2M apps do not support scaffolding.** The command creates the app, prints the credentials and scopes, and stops — no project directory and no `app-config.json` are written, so `brevo app upload`, `brevo app scaffold` and `brevo app start` do not apply to one. Scopes must be named at creation, since there is no config file to seed them from later — but they are not permanent: `brevo app scopes update` (below) changes them afterward. The credentials stay retrievable with `brevo app credentials --app-id <id> --reveal-secret`. Under `--json` the response carries `authType: "m2m"` and `scopes` and omits `redirectUri`, `directory` and `scaffolded` — `appType` stays `"oauth"`, since M2M is a flow within the OAuth app type rather than a third type.

Creating a consent-based OAuth app is otherwise unchanged: its `auth` block still sends no `type` key at all, so nothing about the existing path moves. (Its request body does gain the `app_type` field described below, as every create does.)

Interactively, an M2M app's scopes are now **picked from the IdP's live scope catalog** instead of typed. `brevo app create` → *Machine to Machine* shows a multi-select of every scope your account can grant — the same catalog `brevo app available-scopes` prints, read fresh from the IdP each time (`https://oauth.brevo.com/realms/partner/scopes`, or wherever `BREVO_OAUTH_BASE_URL` points) — grouped under the catalog's own category headings with each scope's description beside its name. A category heading is itself selectable, as a shortcut: picking `Account — all 6 scopes` ticks every scope in that section so you can see what was granted and untick any of them again (dropping one unticks the heading, which means "all of these"). Scopes can equally be ticked one at a time, or `<a>` pressed for everything. A heading is never a scope — the app is created with the ticked names. Nothing is pre-selected and at least one scope is required, because an M2M grant has no consent screen anyone ever reviews. If the catalog cannot be read the CLI says so and falls back to the previous comma-separated prompt, so an IdP hiccup never blocks creating an app. `--scopes` is unchanged and still skips the picker entirely (and the round trip behind it); `brevo app available-scopes` prints exactly what it printed before.

`brevo app create` now also tells the API **which kind of app it is creating**, as a top-level `app_type` on the create request: `oauth.consent`, `oauth.m2m`, `ui_app.actionLink` or `brevo_function`. Previously the app type was only implied by which block the body carried, leaving the endpoint to infer it. Nothing else moves: the value is derived from that same block (so it cannot contradict it), `brevo app upload` sends no `app_type`, the `app_type` key in `app-config.json` keeps its own separate one-word vocabulary (`oauth` / `ui` / `function`) and is still never sent anywhere, and every command's `--json` output is unchanged.

**New: `brevo app scopes update --app-id <id> --scopes "<a,b,c>"`** changes an existing M2M app's granted OAuth scopes after creation — the gap the paragraphs above call out. There is no separate add/remove mode: omitting `--scopes` opens the same interactive scope picker (or, when the catalog can't be read, the typed prompt) that `app create` uses, but pre-filled with the app's *current* scopes, so ticking/unticking or editing that starting point produces the complete new list. Passed directly, `--scopes` is that same full desired set — not a delta — so it replaces the app's scopes outright; anything left out is removed. Either way the command shows a current → new diff (calling out any removal) and asks to confirm before applying (skip with `--yes`); a request that would not change anything exits `0` without calling the API. It is refused for anything other than an M2M app. This depends on a scopes-only backend endpoint (tracked separately) that had not shipped at the time this command was built — treat the exact request/response shape as unverified until a follow-up confirms it against the live API.

**New: `brevo app token --app-id <id>`** mints a short-lived M2M access token for an app and prints the Bearer `access_token` and `expires_in`. Add `--scope "<a,b,c>"` to request a subset of the app's granted scopes; omitted, the token covers the app's full granted set. It is refused for anything other than an M2M app, and the token is printed in full rather than cached — it is short-lived by design and never written to `~/.brevo/credentials.json`. Like `app scopes update` above, this depends on a backend token-mint endpoint (tracked separately, "brevo app token [Backend]") that had not shipped at the time this command was built — treat the exact request/response shape as unverified until a follow-up confirms it against the live API.

**New: `brevo app secret rotate --app-id <id>`** rotates an M2M app's client secret — for when it's leaked, or just as routine hygiene. The old secret stops working immediately, so it asks to confirm before rotating (skip with `--yes`). It prints the **new** `client_secret` once, in full: unlike `app credentials`/`app create`, there is no `--reveal-secret` gate here, because the whole point of calling this command is to get the new secret back — including from a non-interactive rotation script, where a TTY-gated reveal would leave the command unable to ever return the value it exists to produce. Store it in a secret manager right away; it stays retrievable afterward with `brevo app credentials --app-id <id> --reveal-secret`. It is refused for anything other than an M2M app. Like `app scopes update` and `app token` above, this depends on a backend rotate endpoint (tracked separately, "brevo app secret rotate [Backend]") that had not shipped at the time this command was built — treat the exact request/response shape as unverified until a follow-up confirms it against the live API.

**Fix (BEX-488): `brevo app scaffold --app-id <id>` now correctly refuses an M2M app**, instead of silently fabricating a project directory and `app-config.json` for one. M2M apps have never supported scaffolding — that has always been documented — but nothing previously enforced it for the "bootstrap" form of `app scaffold` (setting up an empty directory for an app that already exists), so naming an M2M app's ID would build it a local project as if it were an ordinary OAuth app, one that `app upload`/`app start` could then go on to (incorrectly) act on. The interactive bootstrap picker also no longer offers M2M apps as a choice. `brevo app upload`, `brevo app install`/`app uninstall` and `brevo app submit`/`app status`/`app withdraw` already correctly refused M2M apps (the last three because M2M is private-only, and install because M2M apps carry no UI-app material) and are unaffected by this change.
