**An authored `sandbox` is refused everywhere it can be written.** Stripping it from server echoes only covered the inbound direction — `brevo app upload` sends the file's `ui_app` block verbatim, so a `sandbox` hand-added to `app-config.json` used to travel to the wire and come back an opaque `400`. `validateUiApp` now refuses it by name at the `ui_app` root and on any `surface_point_list` entry (`ui_app.sandbox is not authored in app-config.json …`), ahead of the per-entry checks and before any network call. Refused rather than dropped on the way out, deliberately: `sandbox` is an embedded page's whole permission set, the platform stamps it at write time and applies the stored value verbatim with no default of its own, so silently discarding an authored one would leave a partner believing their value was in force. `sandbox` also joins `link_target`, `version` and `extension_point_name` as a server-stamped key stripped from `ui_app` echoes, so it never lands in `app-config.json` and never shows up as drift.

**`brevo app create --ui-config` now refuses every key it cannot honour instead of dropping it.** The file was read as a fixed key set, so anything else vanished with no error. Keys that belong to a different extension type are refused by name on this `actionLink`-only route, and the four platform-stamped keys (`link_target`, `sandbox`, `extension_point_name`, `version`) get their own message: those are not authored anywhere, so it says to remove the key rather than to move it into `app-config.json`. Both refusals fire before any registry read, and the platform-owned list is derived from the app type's `wireOnlyKeys` so it cannot drift from the keys the CLI strips.

**Iframe extensions remain pre-GA and are not in this release's surface.** The authoring path is built (`brevo app create`'s *Iframe* integration type, the per-entry `iframe_href` / `layout` / `modal_size` / `modal_height` fields, the private-only rule, and the two translated platform refusals) but is gated at build time: `FEATURE_STAGE['ui-iframe-type']` is `'preview'`, so a published build offers no *Iframe* choice and refuses a hand-authored `iframeExtension` block before any round trip. Action links are the whole of the UI-app surface a published build can author, exactly as before. The gate exists because the platform is not ready on either side — its extension-point registry has no slot enabled for `iframeExtension`, and authoring is behind a per-account rollout flag that is off by default — so an ungated choice would dead-end for every partner in a way that reads as a CLI bug. Internal testing is `PREVIEW=1 yarn link:dev`, as with every other gated feature.
