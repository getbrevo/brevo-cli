**The iframe `sandbox` is authorable per entry, on a private app's `iframeExtension` entry only (BEX-498).** The platform sets the default and stamps it on every entry; a private developer may add permissions from the list the platform allows for that slot. The policy is read from the platform's surface-points answer (`metadata.sandbox`: a `default` and an `allowed` list), so the CLI keeps no token list of its own. `brevo app create` asks *Does your page need extra iframe permissions?* — a multi-select of the allowed permissions the default does not already grant — only when the platform publishes that policy for the slot; choosing none writes no `sandbox` (the platform default applies), choosing some writes the whole string, e.g. `"allow-scripts allow-same-origin allow-forms"`. A hand-added entry-level `sandbox` is checked for shape only (a space-separated list of `allow-*` tokens, no repeats); the platform decides which tokens a slot permits and its `400` naming an offender is shown as it arrives. `sandbox` is still refused by name at the `ui_app` root, on an `actionLink` entry and on a public app, before any network call. An entry that authors none is left alone: the platform's stamped default is never written back into `app-config.json` and never reads as drift in `brevo app upload` or `brevo app install`, while an authored value is kept on write-back and shown in the upload diff. Until the platform serves the registry metadata, no question is asked and no `sandbox` is written.

**`brevo app create --ui-config` now refuses every key it cannot honour instead of dropping it.** The file was read as a fixed key set, so anything else vanished with no error. Keys that belong to a different extension type are refused by name on this `actionLink`-only route, `sandbox` among them (it is authorable on a private iframe entry in `app-config.json`), and the three platform-stamped keys (`link_target`, `extension_point_name`, `version`) get their own message: those are not authored anywhere, so it says to remove the key rather than to move it into `app-config.json`. Both refusals fire before any registry read, and the platform-owned list is derived from the app type's `wireOnlyKeys` so it cannot drift from the keys the CLI strips.

**Iframe extensions remain pre-GA and are not in this release's surface.** The authoring path is built (`brevo app create`'s *Iframe* integration type, the per-entry `iframe_href` / `layout` / `modal_size` / `modal_height` fields, the private-only rule, and the two translated platform refusals) but is gated at build time: `FEATURE_STAGE['ui-iframe-type']` is `'preview'`, so a published build offers no *Iframe* choice and refuses a hand-authored `iframeExtension` block before any round trip. Action links are the whole of the UI-app surface a published build can author, exactly as before. The gate exists because the platform is not ready on either side — its extension-point registry has no slot enabled for `iframeExtension`, and authoring is behind a per-account rollout flag that is off by default — so an ungated choice would dead-end for every partner in a way that reads as a CLI bug. Internal testing is `PREVIEW=1 yarn link:dev`, as with every other gated feature. Within that gated path, `layout` and `modal_size` are now written into `app-config.json` for every answer including the defaults (`"modal"`, `"large"`), rather than omitted when the answer matched the platform's fallback — an entry states how it presents instead of implying it by an absent key. Absent remains valid on the wire and in `validateUiApp`, so a config authored before this still uploads unchanged; the fields are still written only where they apply, so an action slot's menu entry carries no `layout` and an `inline` card carries no `modal_size`. An `inline` card is now also asked **how tall** it should be, pre-filled with the slot's own `default_size.height` from the extension-point registry — the one piece of card geometry the slot cannot decide for the partner, because an inline card IS the embedded page. A blank answer keeps that registry default, an answered one overrides the height alone (a `width` the slot declared survives untouched), and the answer is judged by the same axis grammar `brevo app upload` enforces on the file, so the prompt cannot accept a value the block it lands in is then refused for. Asked for `layout: "inline"` and nothing else: a modal is sized by `modal_size`, an action slot renders no card, and an action link's card shows a CTA rather than a page.

**A malformed registry default card size is no longer seeded into a new app's config.** `brevo app create` seeds each entry's `size` from the picked slot's `default_size` (BEX-461), and the sanitizer on that seed dropped only blank axes — so a unit-less value served by a registry predating the grammar (`"100"` rather than `"100px"`) was written into `app-config.json` and then refused by the CLI's own `validateUiApp`, in the very flow that had just authored it. The seed is now judged by the authored-size grammar itself, which is exported and shared by all three of its readers — the file check, the new card-height prompt, and this sanitizer — so they cannot drift apart.

**A framing/CSP checklist for iframe apps (BEX-498).** After `brevo app create` authors an iframe app, a second box, *Before your iframe renders*, lists what the embedded page must do for the frame to load: no `X-Frame-Options: DENY` or `SAMEORIGIN`; a `frame-ancestors` that allows Brevo's app origin(s) or is omitted; an absolute `https://` `iframe_href`; no reliance on third-party cookies; and the reminder that the platform sets the sandbox default and a private app may add permissions from the list the platform allows. `brevo app upload` prints a one-line pointer to it after an iframe upload. Text mode only, never under `--json`, never for action links. The strings live in `preview-messages.ts` behind `__BREVO_PREVIEW__` and are asserted absent from a published build.
