Replace `brevo app update` with `brevo app upload` (BEX-250).

`brevo app update` is removed entirely — no stub, no forwarding shim. `brevo app upload` takes only `--yes`/`--json` and has no edit flags (`--app-id`, `--name`, `--redirect-uri`, `--scope`, `--logo-uri` are all gone); change an app's name, redirect URLs, scopes, logo, or version by editing `app-config.json` directly, then run `upload`. `distribution_type` is the exception: it is immutable after `app create` — the server rejects any attempt to change it via upload, and the CLI errors first with a message telling you to restore it (or create a new app), before anything is pushed.

`upload` always fetches the app's current remote state and renders a local-vs-server diff before pushing — even under `--yes` (skips the confirmation prompt but still shows the diff) or `--json` (the diff comes back as structured data instead of a prompt). If nothing differs, it exits 0 with "already up to date" and makes no network push. Otherwise it POSTs the full local `app-config.json` to `POST /v3/app-store/apps/{appId}/upload` and writes the server-confirmed state back into `app-config.json` on success.

On success, `upload` now reads the server-confirmed version from either `app_version` or `version` in the upload response, so the bumped version is always persisted to `app-config.json` and printed — instead of silently keeping the old value when the server returns it under `version`.

Likewise, `upload` now reads the server-confirmed `distribution_type` from the top level of the upload response, where the server has always returned it — the response's `auth` block only carries `scopes` and `redirect_uris`. Previously the CLI looked for it nested under `auth` (a shape no server build ever emitted), so the write-back silently kept whatever `app-config.json` already said instead of the server's echo. If the field is ever missing from a response, the write-back still falls back to the local value. The response's `auth.scopes`/`auth.redirect_uris` may also come back `null` (e.g. UI-only apps whose snapshot has no OAuth block) — the write-back treats `null` as absent and keeps the locally-sent values.

Breaking change: any script or CI job invoking `brevo app update` (or its `--scope`/`--redirect-uri`/`--name`/`--logo-uri` flags) needs to switch to editing `app-config.json` and running `brevo app upload` instead.

`brevo app scaffold` gains `--app-id <id>`, which sets the current directory up for an app that already exists: it fetches the app, writes `app-config.json` plus the base files, then continues into the usual feature flow. This is what `brevo app update --app-id <id>` migrates to. That invocation had no successor otherwise — `upload` reads the linked project in the current directory only, so anyone who drove `update` by ID from an arbitrary directory was told to edit an `app-config.json` they had no way to obtain (`app create` makes a *new* app; `scaffold` without the flag requires a config to already be there). The flag is refused, before any network call or write, when the directory is already linked to a different app; naming the app it is already linked to changes nothing. With no local config to read the app type from, bootstrap takes it from the server, so bootstrapping a UI app writes its config and reports that there are no features to scaffold. Running `brevo app scaffold` with neither a config nor `--app-id` now lists all three ways forward instead of only pointing at `brevo app create`.

`brevo app scaffold` no longer needs `--app-id` at all when run interactively. In a directory with no `app-config.json` it now explains there is no app here, asks "Set this directory up for an app you already have?" (default yes), and on yes shows the same app picker `app delete` and `app withdraw` use — so recovering a project no longer requires knowing the app's ID, which is the common case after a fresh clone, a new machine, or an `app create --json` that ran in CI. Declining is a normal outcome: it exits `0` after printing the remaining routes, rather than erroring. The offer is interactive-only — under `--json` or off a TTY the command raises the same no-config error as before, so existing scripts and CI jobs are unaffected and `--app-id` remains the non-interactive entry point.

Bootstrapping now refuses two cases that previously produced a silently wrong project. First, a directory **inside** an existing app project: `app-config.json` is read from the current directory only and never looked up the tree, so running scaffold one level down used to create a second, nested config — after which `brevo app upload` from that directory pushed the wrong app without a warning. It now names the enclosing project and stops before any network call. Second, a **UI app that has never been uploaded**: the platform sources a UI app's `ui_app` block from its latest upload snapshot, so a never-uploaded UI app has no block to return, and a config written without one does not read as an incomplete UI app but as a valid OAuth app (the block's presence is the app-type discriminator) — whose next upload would push an `auth` block where `ui_app` belonged. It now refuses and explains, instead of writing that config. A half-configured OAuth app (client ID issued, no callbacks yet) is unaffected and still bootstraps.

The `ui_app` block written by a bootstrap is stripped of the keys the platform owns — `link_target`, the server-managed snapshot `version`, and each entry's derived dotted `extension_point_name` — so a bootstrapped `app-config.json` matches a hand-authored one and the next `brevo app upload` neither reports phantom drift nor sends a key the endpoint rejects. This is the same normalization the upload diff and write-back already applied, now shared by all three rather than reimplemented per call site.

To make that migration self-explaining, `brevo app update` now answers with a message naming `brevo app upload` and explaining that the edit flags are gone (edit `app-config.json`, then upload) instead of Commander's `unknown command 'update'` — which suggested `create`. It is still not a shim: nothing is forwarded, nothing is uploaded, and it exits `1` (`--json` gives the usual `{"error":{…}}` envelope). The message is reachable however the old invocation was typed — with any of the removed flags, with stray arguments, and via `brevo app update --help` or `brevo app help update`, neither of which prints a usage screen or exits `0` any more. It does not require being logged in. `update` stays absent from every help screen.

The CLI no longer injects `cli_version` into the `app create` and `app upload` request bodies. The upload endpoint binds its body strictly and rejects unknown top-level keys with a 400, and the CLI version already reaches the backend on every request via the `User-Agent` header (`brevo-cli/<version> (<os>; auth=<method>)`), so the body field was both redundant and a hard failure against strict server builds. Relatedly, `brevo app create`/`brevo app scaffold` no longer stamp an informational `cliVersion` field into `app-config.json` — nothing ever read it, and it recorded only the version that scaffolded the project. Existing `app-config.json` files that carry the field keep working; the CLI ignores it and drops it on the next config write-back.

`app-config.json`'s redirect-URL list is renamed `auth.redirectUrls` → `auth.redirectUris`, matching the wire key (`redirect_uris`). Backward compatible: the CLI still reads the old key (the new one wins if both are present), and any command that writes the file back (`upload`, `app start`'s URL registration) migrates it to `redirectUris` automatically. New scaffolds write `redirectUris` from the start. Note for mixed-version teams: once a file is migrated, older CLI releases (which read only `redirectUrls`) will report "no redirect URLs" on upload — re-add the old key or upgrade the CLI.

UI apps no longer carry an OAuth block (BEX-290): a UI app's `app-config.json` now has exactly `auth: {}` — an empty object, no `scopes`, no `redirectUris` — and `brevo app create` no longer applies the narrower UI-app scope defaults (the OAuth defaults are unchanged). On the wire, UI-app creates and UI-app uploads both omit the whole `auth` key; the `ui_app` block is what marks the omission deliberate (without it, create reads the app as an OAuth app missing its callbacks). `brevo app upload` enforces the shape both ways: a UI-app config with no `auth` at all is rejected with instructions to set it to `{}`, and one still carrying `scopes`/`redirectUris` is rejected with instructions to remove them. The dev-era `auth: { "type": "none" }` marker is obsolete — any `auth.type` still on disk is dropped when the config is read, and migrated away on the next write-back.

The unused `permittedUrls` and `support` sections are gone from scaffolded `app-config.json` files for both app types — nothing ever read them. Existing files that still carry the sections keep working; the CLI ignores them and drops them on the next config write-back.

The interactive `brevo app create` prompt order is now name → distribution → app type → type-specific prompts → logo (distribution moved ahead of the app-type question). Flag-driven and non-interactive runs are unaffected.

The UI-app create flow is now registry-driven (BEX-361): choosing **UI app** first fetches the available placements from `GET /v3/app-store/surface-points` and builds every placement choice (record pages, kind, positions, and the record-context checkbox) from the fetched rows — labels come from the registry's own `surface_point_name`, and the selected rows' `extension_point` names are written verbatim to `surface_point_list`. There is deliberately no offline fallback: if the fetch fails, UI-app creation aborts with an actionable error (OAuth creation is unaffected). A new integration-type prompt follows placement — **External link** is selectable, **Modal iframe** is shown disabled as "coming soon" — and the heading/subheading/redirect-link prompts now describe what each field renders as (link label, tooltip, destination URL). When the selected placements declare `allowed_context_field`, the context prompt becomes a checkbox of their union instead of free text.
