`ui_app.surface_point_list` entries accept an optional `size` at the same level as `context` — the card-size override for the widget card that placement renders (BEX-416). Each axis is a CSS length string: `"<positive integer>px"` (absolute) or `"<1-100>%"` (relative to the host slot's box), e.g. `{ "width": "280px" }` or `{ "height": "50%" }`. Both axes are optional — an omitted axis stays on the host record page's per-slot default, and an empty `size` object authors nothing (the platform stores it as no size at all). Validated shape-only in `validateUiApp`; the platform remains the authority on anything registry-dependent. Partner-authored, so it round-trips through the upload diff and write-back like `label`.

`label`, `more_info`, `redirect_link` and `modal_iframe_url` moved from the `ui_app` root into each `surface_point_list` entry (BEX-426), so an app on several slots can label each placement differently and deep-link each somewhere else — completing the per-entry migration `context` and `size` started. Hard move: `validateUiApp` refuses the root spellings by name with a migration hint, per-entry violations name their entry (`ui_app.surface_point_list["<slug>"].label: …`), and the per-type rules (actionLink: `redirect_link` required, `modal_iframe_url` refused; iframeExtension: the reverse) now run on every entry. `link_target` then followed them onto each entry, leaving `extension_type` as the only field at the `ui_app` root: it says where THAT entry's `redirect_link` opens, so a root copy could only describe every placement identically, and the platform's read path already treated the entry as the only source. It stays out of `app-config.json` — `brevo app upload` injects `_blank` onto every `actionLink` entry, the write-back strips the server's echo of it, and the upload diff normalizes it away on both sides — so `validateUiApp` refuses a leftover root `link_target` by name with a _remove it_ hint, checks a hand-authored per-entry value against the `_blank` pin, and refuses one on an `iframeExtension` entry, which embeds its URL rather than navigating to it. `brevo app create`'s UI-app flow now authors exactly one placement — the record-page prompt is a single-select — and the created-app box points at `app-config.json` for adding more placements, each carrying its own label and destination.

`brevo app delete` now warns before the confirmation prompt that deleting an app also removes it from every account where it is installed or published, and that installs and credentials cannot be recovered. `--force` still skips both the warning and the prompt.

The preview commands `brevo app deploy` / `brevo app rollback` are renamed to `brevo app install` / `brevo app uninstall`, matching the platform resource they act on (`POST`/`DELETE …/installs`). Their JSON output keys follow (`installed` / `uninstalled`, reason `NOT_INSTALLED`). Both commands are pre-GA and absent from published builds, so nothing shipped changes; the wire contract (including the `deploy_client_id` body field) is untouched.

`brevo app create`'s UI-app placement prompt now labels each choice with the registry's own values — `section_name — component_type`, e.g. `headerMenu — action` — instead of a CLI-owned prettifying map (`Header "More" (•••) menu — menu entry`). The map gave every server-supplied slot a second name to keep in step with the platform and fell back to the raw token for anything it didn't know, so the prompt mixed two vocabularies; the page prompt already showed `location_name` verbatim for the same reason. Choice values are unchanged (still the row's `surface_point_name` slug), so authored configs are unaffected. Pre-GA and absent from published builds.

`brevo app install` and `brevo app uninstall` now refuse an app that is not a UI app. Only a UI app is installed into an account — the rule the capability matrix already encoded and nothing on the install path consulted, so an OAuth app installed with a `201` and rendered nothing (the installs endpoint has no app-type check of its own). The refusal reads the app type from `app-config.json` in a linked project, or from the app record otherwise, and is biased to refuse only when it is sure: a record carrying OAuth material is refused, one carrying none is allowed through. A read failure does not block, same policy as the upload gate. `uninstall` is gated on the app type but still not on `version` — an app installed by an older CLI must stay removable — which does mean an OAuth app installed by a CLI predating this check can no longer be uninstalled; the record it would remove is one nothing reads. The two checks now share a single app read where they used to make two, and both read `app-config.json` only for the app that config actually describes: `--app-id <other-app>` run inside a linked project is gated against the app it names, not the directory's — previously the local config answered unconditionally, so an OAuth app named explicitly from inside a UI-app project passed both checks on the strength of a config that was not about it. Naming an app now costs one read; resolving it from the linked project still costs none.

Both commands now name the target account, not just its ID: `installed into Acme Retail (account 4043630)` for a picked sub-account, and `installed into Acme Retail (your own account, ID 12345)` when the account resolved to the caller's own — the two paths where the CLI chooses the account and the user has no number of their own to check it against. The company name comes from responses those paths already read, so nothing costs an extra request. An explicit `[account-id]` is not looked up and its wording is unchanged (`installed into account 99999`), so CI output is untouched. `--json` gains an additive `accountName` when a name was resolved; `accountId` is still the raw identifier.

`--help` examples for `--app-id` now show a UUID instead of `42`, on every command that takes the flag. An app ID is a UUID — `app create` issues one — so the old examples taught the wrong shape uniformly.

`brevo app create`'s UI-app integration-type prompt no longer lists Iframe as a disabled "coming soon" choice — Link (`actionLink`) is the only choice offered until iframe authoring is ready. The question is still asked, so the user is told what they are getting, and `brevo app upload` still accepts a hand-authored `iframeExtension` block. Pre-GA and absent from published builds.

The *Next steps* box after a UI app is created lines its hints up again. The two step lines carried hard-coded padding for commands one character apart in length, which put `brevo app upload`'s note ten columns right of `brevo app install`'s inside the same box; the column is now derived from the widest command in the list. The OAuth box's wording and spacing are unchanged.
